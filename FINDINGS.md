# What Client Watcher looks for

Client Watcher reports **passive signals**, not confirmed exploits. “Exposure” means the indicated material was observed in browser-accessible content; “potential” means the finding needs manual review. The popup retains the affected origin, a sanitized page path, and redacted evidence; it does not retain query strings, fragments, or credential values found in scanned storage and scripts. Long, encoded, and common credential-bearing path segments are redacted.

| Finding (rule ID)                                                  | How it is detected                                                                                                                                                                             | Why it matters                                                                                                                                                                |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sensitive browser storage (`storage-sensitive`)                    | Checks the first 100 keys in each of `localStorage` and `sessionStorage` for auth-, token-, or secret-like names with values of at least 8 characters. Excludes known public client-key names. | Page scripts can read these values; an injection or third-party script could obtain a session credential. A matching name alone does not establish that a value is sensitive. |
| Session cookie readable by JavaScript (`cookie-httponly`)          | Finds session-like cookie names, including `sid` and common framework session IDs, whose `HttpOnly` flag is absent.                                                                            | Page scripts can read the cookie, increasing the impact of script injection. The name is only a heuristic for whether it holds a session.                                     |
| Session cookie without `Secure` (`cookie-secure`)                  | On HTTPS pages, finds session-like cookies whose `Secure` flag is absent.                                                                                                                      | Such cookies may be sent over unencrypted HTTP to an eligible host.                                                                                                           |
| No enforced CSP (`header-csp`)                                     | Checks whether the main document response includes a `Content-Security-Policy` header; a report-only policy does not count.                                                                    | An enforced policy can limit some injection impacts. Missing CSP is a defense-in-depth lead, not evidence of XSS.                                                             |
| CSP permits inline scripts (`header-csp-unsafe-inline`)            | Checks enforced script directives for `'unsafe-inline'` without a nonce or hash, accounting for other CSP headers that restrict scripts.                                                       | Permissive inline script rules can reduce CSP's protection against injection; this is not proof of XSS.                                                                       |
| CSP permits any script source (`header-csp-wildcard-script`)       | Checks whether the effective script directives permit `*` without another CSP header restricting them.                                                                                         | A wildcard can allow scripts from untrusted origins if other defenses fail.                                                                                                   |
| CSP does not restrict scripts (`header-csp-no-script-restriction`) | Checks for CSP headers that lack both `script-src` and its `default-src` fallback.                                                                                                             | A CSP limited to other resource types may not constrain scripts at all.                                                                                                       |
| No HSTS (`header-hsts`)                                            | On HTTPS main document responses, checks for `Strict-Transport-Security`.                                                                                                                      | HSTS can protect subsequent visits from HTTP downgrade. A missing header alone is not an exploitable vulnerability.                                                           |
| Ineffective HSTS (`header-hsts-disabled`)                          | Checks for HSTS headers with no valid positive `max-age`, including `max-age=0`.                                                                                                               | An HSTS header can be present while providing no upgrade protection.                                                                                                          |
| Supabase secret key exposed (`supabase-secret`)                    | Looks for the `sb_secret_` key pattern in sampled storage and inline or observed external JavaScript.                                                                                          | This is a server-side credential that should not be shipped to browsers. Public `sb_publishable_` and anon keys are not flagged.                                              |
| Supabase service-role JWT (`supabase-service-role`)                | Decodes bounded JWT candidates in storage and JavaScript and checks for `iss: supabase` and `role: service_role`.                                                                              | A valid service-role token can grant privileged access. JWT claims are unverified; this check cannot establish that the token is genuine or active.                           |
| Firebase service account exposed (`firebase-service-account`)      | Looks for service-account type, client email, private-key field, and a PEM private-key marker together in storage or JavaScript.                                                               | A real service-account private key belongs on a trusted server, not in client-accessible data. Public Firebase web configuration is not flagged.                              |
| Private key in JavaScript (`private-key`)                          | Finds PEM private-key headers in sampled inline or observed external JavaScript, unless classified as a Firebase service account.                                                              | A shipped private key may let others impersonate its holder; the scanner does not verify whether it is real or usable.                                                        |
| URL content assigned to HTML (`dom-location-html`)                 | Matches direct assignments from `location.search` or `location.hash` to `.innerHTML` or `.outerHTML` in sampled scripts.                                                                       | This is a possible DOM-injection path. It is a narrow code pattern, not a confirmed XSS or a complete data-flow analysis.                                                     |
| Auth token in hydration data (`hydration-token`)                   | Looks for long token values under specific auth-token names in Next.js `__NEXT_DATA__` or React-style `__INITIAL_STATE__` / `__PRELOADED_STATE__` script content.                              | Hydration data is readable by browser scripts; embedded tokens deserve review for scope and lifetime.                                                                         |
| Next.js server runtime config exposed (`next-runtime-config`)      | Parses the `__NEXT_DATA__` script and reports a nonempty `serverRuntimeConfig` object.                                                                                                         | Server-only configuration may have been serialized into the page. The extension does not assume every property is secret.                                                     |
| Password form submits over HTTP (`password-form-http`)             | Checks the resolved action URL of forms containing a password input.                                                                                                                           | A submitted password could travel over an unencrypted connection.                                                                                                             |
| Sensitive URL query value (`url-sensitive`)                        | Checks page and observed subrequest query parameters with specific credential-like names and values of at least 8 characters.                                                                  | Query values can appear in browser history, logs, or referrer information. The value is never saved in the finding.                                                           |
| OAuth token in URL fragment (`url-fragment-token`)                 | Checks page fragments for long `access_token`, `refresh_token`, or `id_token` parameters.                                                                                                      | Fragments are not sent in HTTP requests, but page scripts and browser history can still access them.                                                                          |

**Coverage limits:** storage sampling stops after 100 keys per area or 2,048 characters per value; inline scripts stop after 100 scripts or 256 KiB total; forms stop after 100; external script inspection stops after 20 responses per tab or 256 KiB per response. The popup marks unavailable or skipped sources as partial or not inspected. “Checked” means sampled, not exhaustive. No active validation of backend permissions, token validity, or exploitability is performed.
